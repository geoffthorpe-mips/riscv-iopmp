== Introduction

On a RISC-V platform, there may be requesters other than RISC-V harts that can initiate bus transactions, potentially exposing the system to vulnerabilities such as DMA attacks. Whereas the PMP/ePMP ISA extensions cite:[PrivISA] provide an interface to restrict accesses allowed from a given RISC-V hart, there is currently no standardized interface to provide such restrictions on transactions emitted by other initiators. The current specification defines the interfaces and behaviors of a Physical Memory Protection Unit for Input/Output Devices, or "IOPMP", to address this requirement.

=== Target System Scaling
The IOPMP architecture is intended to scale from small embedded systems to large heterogeneous platforms with many independent requesters and protection regions.
An implementation can support hundreds of active request-role IDs (RRIDs), and the architecture allows up to 65,535 IOPMP entries in one IOPMP instance.
This scale motivates the two-stage mapping hierarchy described in this specification: an RRID first selects one or more memory domains, and each memory domain then selects the IOPMP entries that define the protected address regions and permissions.

The same scaling goal also motivates optional mechanisms that reduce lookup latency or implementation cost in larger systems, such as non-priority entries, table-reduction formats, and implementation-specific caching of protection checks.

=== Relationship to IOMMU

The RISC-V IOMMU (cite:[IOMMU], Input-Output Memory Management Unit) is a system-level generalization of the ISA's MMU mechanism, in the same way that the IOPMP is a system-level generalization of the PMP. So a comparison of the two ISA mechanisms, PMP and MMU, helps when comparing the corresponding system-level mechanisms, IOPMP and IOMMU. For example, the PMP and MMU both provide a form of access-control, but they are very different in their usage, benefits, and complexity of implementation, and so they are typically seen as complementary concepts (rather than alternatives) - the same general observation is also true about IOPMP and IOMMU. Some other similarlities;

* PMP and IOPMP implement fixed-sized rule tables, whereas MMU and IOMMU use dynamic data structures stored in main memory. As such, PMP and IOPMP are more amenable to meeting real-time requirements (including the possibility of deterministic latency bounds) than MMU and IOMMU.
* PMP and IOPMP both provide basic access-control at the physical address layer, whereas MMU and IOMMU implement virtual addess spaces. As such, PMP and IOPMP are both likely to have a significantly lower implementation complexity than their MMU/IOMMU counterparts.

The analogy between ISA mechanisms and their system-level counterparts is less helpful when considering trust boundaries. In the ISA, the PMP lets M-mode impose constraints on access to the physical address space, whereas the MMU lets S-mode impose a virtual address map - the two mechanisms straddle (different) privilege boundaries. At the system-level there is no equivalent concept - the trust boundary is between whichever domain configures the IOPMP/IOMMU and whichever domain influences the I/O addresses used by the initiating device.

Consider an operating system (in S-mode) using an MMU to manage user-space (U-mode), where an application reads and writes I/O buffers that are produced and consumed by a DMA-capable device. Are IOMMU and/or IOPMP required to control that device's transactions?

* If the device driver runs in the OS kernel and manages device I/O on the application's behalf, it can provide physical addresses directly to the device and there is no need for an IOMMU.
* Conversely, if the OS allows the application to provide I/O buffer descriptors directly to the device, then an IOMMU may be required to ensure the application can't use device I/O to circumvent its virtual address space. Optimized data-path solutions are an example of this pattern.
* In both cases, an IOPMP is required at the system level if and only if a PMP is used within the hart to constrain the OS as a whole. Here we see that the IOPMP requirement is orthogonal to the IOMMU requirement.
